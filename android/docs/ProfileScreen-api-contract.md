# 画像页与设置页 · 数据需求（给后端）

> 客户端侧的对接需求清单；后端侧的应答与实现约定见 [`backend/docs/ProfileScreen-api-contract.md`](../../backend/docs/ProfileScreen-api-contract.md)（同名姊妹文档）。

## 现状

画像页（`ProfileScreen`）雷达图 7 轴中 6 轴、人格判定的一半判据是前端写死的固定值；「重新生成报告」按钮是假刷新。需要后端补真实数据。

设置页（`SettingsScreen`）收集的用户信息（昵称、性别、年龄、语气偏好）目前只存在客户端本地，后端与 Agent 完全看不到，等于没生效。

## 需要的数据

### 1. ACT 六维心理指标

每用户基于对话计算的 6 个 **0~1 浮点**。英文名仅为讨论占位：

| 维度 | 界面展示名 | 含义 | 方向 |
|---|---|---|---|
| psychological_flexibility | 走出情绪 | 多容易从坏情绪里走出来继续过日子 | 越高越好 |
| emotional_openness | 接纳感受 | 愿不愿意承认和接纳自己的感受 | 越高越好 |
| cognitive_readiness | 适合深聊 | 当前状态适不适合做深度自我剖析 | 越高越好 |
| cognitive_fusion | 想法绑架 | 多容易把负面念头当真、被它牵着走 | 越高越困扰 |
| experiential_avoidance | 躲避情绪 | 多习惯用刷手机/忙起来等方式躲开情绪 | 越高越困扰 |
| values_alignment | 活出自己 | 日常行为与自己在乎的东西的对齐程度 | 越高越好 |

前端按原值展示

### 2. 人格类型与重新生成

后端输出九型人格的枚举结果

`beginner` 初识者 / `night_watcher` 守夜人 / `watcher` 守望者 / `storm_rider` 风暴骑手 / `navigator` 航海者 / `anchor` 定锚者 / `light_weaver` 织光者 / `lone_wanderer` 独行者 / `wind_messenger` 风信使

现有前端判定规则（`ProfileScreen.kt` 的 `determinePersonality()`）可作参考，后端可自行迭代。

另需一个触发重新生成的手段，供「重新生成报告」按钮使用：只重新判定人格类型（不动六维、价值词等其他字段），新结果通过人格查询端点可见即可，前端不接单独的结果通道。建议加频控（如每用户10s一次）。

### 3. 用户信息同步

设置页收集的四项用户信息需要后端存储，供 Agent 在对话中使用：

| 字段 | 类型 | 取值 | 空值含义 |
|---|---|---|---|
| nickname | string | ≤12 字符 | 未设置，Agent 不用昵称呼叫 |
| gender | string | `male` / `female` | 未设置 |
| age | int | 1~120 | 未设置 |
| tone_preference | string | `gentle`（温和）/ `lively`（活泼） | 未设置 |

- 写入成功服务端要给响应
- 客户端只写不读：本地 DataStore 是设置页展示的数据源，后端仅作 Agent 用途的存储。（本身不调 GET）
- 这些字段可以加到系统提示词里面
- **重置语义**：「重置形象」会把四项全部清空为未设置（客户端本地已这么做），后端值由客户端 `PUT` 空值覆盖即可，无需额外提供删除接口。

## 通用约定

- 旧版 App 忽略未知字段，**后端可先行上线，不用等客户端发版**。
- 为了防止某些字段生成可能耗时较长（万一要用大模型呢），1、2字段可以有三种状态：**就绪**（有值）/ **生成中**（稍后可通过同一查询拉到）/ **没有**。粒度按展示模块计（雷达值一组、人格一枚举、价值词一组），哪个模块算完哪个可拉到，无需凑批。方便前端按需展示
- 画像确定「没有」时后端直接返回空对象即可，前端展示空态引导，无需为新用户特判。
